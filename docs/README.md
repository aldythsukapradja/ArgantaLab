# ArgantaLab Docs Index

This is the map of every markdown doc in the repo — what it is and where to find it, grouped by
the product/system it covers. It does not move or rewrite anything; it's a first pass so "where do
I look for X" has one answer. A later pass can add per-doc status/freshness metadata and
consolidate duplicates — see [Known gaps](#known-gaps-for-a-later-pass) at the bottom.

**Filename convention already in use across the repo** (informal, not enforced): `CONCEPT-` =
exploratory idea, no build yet · `PLAN-` / `BUILD-PLAN` = sequenced implementation steps ·
`DESIGN-` = UI/UX or systems design · `HANDOFF-` = state dump for the next agent/session ·
`AUDIT-` = review of what exists today · `SPEC-` = contract/interface definition · `IMPL-` =
implementation notes for a specific slice · `MAP-` / `*-MANIFEST` = inventory or reference data.
Treat these prefixes as a rough signal of what you're about to read, not a guarantee it's current.

## Known gaps for a later pass

This index is a snapshot over the current file layout — nothing was moved or renamed. Things worth
doing next, if/when it's worth the churn:

- **No living/frozen status per doc.** Filename prefixes (`CONCEPT-`, `HANDOFF-`, etc.) hint at
  intent but nothing marks a doc as current source-of-truth vs. superseded. LashiraBloom in
  particular has three overlapping layers (root `docs/LASHIRABLOOM-*`, flat `docs/lashirabloom/*`,
  and `Openworld Bloom Concept/`) where it's not obvious from the filename alone which one wins —
  the `Openworld Bloom Concept/INDEX.md` claims ground truth for its own scope, but the other two
  layers aren't reconciled against it.
- **Likely-stale duplicate:** `apps/kingdom/dist_site/data/derived/audit.md` mirrors
  `apps/kingdom/data/derived/audit.md` — probably a build artifact that shouldn't be hand-edited or
  indexed as source.
- **No root `README.md`.** The repo has no top-level README pointing here; worth a one-line
  pointer (`See docs/README.md for the docs index`) if this index proves useful.
- **No freshness signal.** Nothing records when a doc was last verified against the actual code.
  A `last-reviewed` front-matter field (see the original proposal) would make staleness visible
  without needing to open every file.
